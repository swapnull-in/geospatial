Find nearby. Then dispatch.

Every "find nearby / ETA / match" system collapses onto three pillars — a spatial index, routing on a road graph, and matching. This lab draws all three: watch a B-tree fail a radius query, a geohash miss the neighbor across a cell edge, a quadtree prune 99% of points, a firehose of pings stay off the database, and a batch of riders match without a race.

The one sentence that proves you understand the field: a B-tree can't serve a radius query because no 1-D ordering of 2-D points keeps both axes local — so you index a space-filling-curve key that bakes 2-D proximity into a 1-D sort, and nearby-search becomes a handful of range scans.

Distance & the brute-force baseline

Proximity starts with measuring distance on a sphere (Haversine, not flat Pythagoras) and the naive nearest-K: measure every point, sort, take K. Correct, and O(n) per query — fine for 10 points, catastrophic for 10M driver locations. That O(n) is the whole reason spatial indexes exist.

Geohash — 2-D into a 1-D key, and the boundary trap

A geohash interleaves lat/lng bits into a string: a shared prefix means a shared cell, so "find nearby" becomes a prefix range scan any KV store does. The trap: two points meters apart can straddle a cell edge and share no prefix — a single-cell scan misses the nearest. The fix is the 9-cell (query cell + 8 neighbors) scan.

The proof: the two pins are ~24 m apart but land in different cells. A single-cell scan finds one and silently drops the other — the #1 geohash bug. Turn on the 3×3 neighbor fan-out and both are found; then you re-rank candidates by true Haversine. Precision 6 (~1.2 km cells) is the find-nearby workhorse.

Quadtree — an index that prunes

A geohash uses one fixed cell size everywhere. A quadtree adapts: a node holds up to capacity points and subdivides into four quadrants only where dense. A range query descends only into quadrants that intersect the query box — whole subtrees that can't match are skipped without looking at their points.

S2 & the Hilbert curve — better locality, hierarchy, region cover

Geohash walks the grid on a Z-order curve, which occasionally makes a long jump where the "Z" snaps back. S2 uses the Hilbert curve, which never jumps — consecutive cells are always edge-adjacent → tighter ranges, fewer false candidates — plus hierarchical cells (parent = a bit-truncation) and region cover.

—
curve pathlong jumpregion cover

The proof: the Hilbert curve's longest step is 1 cell (always edge-adjacent), so a range of 1-D keys maps to a compact 2-D blob. The Z-order curve makes — long jumps back across a quadrant — two cells adjacent in key space can be far apart on the map, which is why S2's locality beats geohash. Parent cells are a bit-truncation (roll dispatch cells up to surge cells for free).

R-tree — indexing polygons, not points

Curve methods index points. An R-tree indexes extents by their minimum bounding rectangle (MBR) — the index behind PostGIS. "Which delivery zone contains this point?" descends only nodes whose MBR contains the point, then runs the exact ray-cast on the few candidates. The MBR is a cheap filter, never the answer.

Expanding-ring kNN — "the nearest 5 drivers"

The dispatch query on an in-memory grid: look in your own cell, then expand outward one ring at a time. The subtle part is termination — once you have K you can't stop, because a point in the next ring might be closer than your current Kth. You may only stop when the Kth distance ≤ the nearest possible point in any unscanned ring.

—

The proof: after collecting 5 candidates the search keeps going one ring — because the Kth-nearest is still farther than the closest edge of the next unscanned ring, so a nearer driver could hide there. It stops the instant that stops being true. Terminating too early returns a wrong "nearest 5"; this is the whole gate.

Geofencing — point-in-polygon (containment, not proximity)

The other half of geo. Proximity asks "what's near me"; containment asks "am I inside this zone" — a delivery area, surge region, "you've arrived" trigger. The primitive is ray casting: shoot a ray and count edge crossings — odd = inside, even = outside. A radius check gets the non-convex case wrong.

The proof: a point that looks like it's "in the middle" of the L-shape is actually in the notch — outside the zone. The ray from it crosses the border an even number of times. A naive center+radius check would wrongly include it; ray casting handles arbitrary non-convex polygons. At scale: R-tree to narrow (Phase 7), ray-cast to confirm.

Proximity at scale — scatter-gather, hot cells, surge

The index is only the retrieval layer; the interview is won in the seams. A nearby query is a scatter-gather over the cell + neighbors whose p99 is the worst shard's — hedge or deadline it. The hot cell (Times Square) is a hot key. Ranking is retrieve→rank, not distance-sort. Surge is a per-cell demand heatmap.

Ranking blends distance with rating/popularity — a 4.8★ at 800 m beats a 3.0★ next door.

The write-path — a firehose that never touches the database

~3M drivers pinging every 4 s ≈ 750k writes/sec. You cannot put that on Postgres. Location is eventually consistent, lossy, and disposable — it lives in an in-memory, city-partitioned, TTL'd geo-index (last-write-wins), rebuildable from the stream. The DB persists trips, not every breadcrumb.

The proof: most pings don't cross a cell → a cheap O(1) overwrite-in-place; the minority that cross do a remove-old + add-new (Redis ZREM+GEOADD). A driver that goes silent ages out via TTL so it stops being matched (no ghost drivers). Under load, widening the ping interval halves the write rate — a named degradation lever. The index is derived state; rebuild it by replaying the stream.

Routing — Dijkstra → A* → Contraction Hierarchies

A road network is a weighted graph. Dijkstra explores a circle in all directions. A* adds a straight-line heuristic to bias toward the goal (an ellipse) — same answer, fewer nodes. Contraction Hierarchies precompute shortcut edges offline so a query touches a fraction of the nodes — sub-millisecond continental routing.

The proof: all three return the same shortest-path cost — but the nodes settled shrink Dijkstra → A* → CH. Naive Dijkstra re-explores the whole graph every query; CH does the heavy work once offline (adding shortcuts) so each query is a bidirectional upward search over a fraction of the graph. CRP then splits topology from the traffic metric so a live-traffic update is a cheap re-customization, not a full re-preprocess.

Dispatch — batched matching, not greedy nearest

Assigning each request its closest driver (greedy) is wrong at the margin: it races (two requests grab one driver) and is globally worse (a driver taken greedily was someone else's only option). The Staff answer is batched global min-cost matching over a short window, committed with an atomic driver-claim.

The proof: on the same batch, greedy leaves riders waiting longer (and can strand one) because it commits locally-optimal choices; the batched min-cost assignment minimizes total wait and a single writer decides the whole batch — dissolving the double-assignment race for free. Each pairing is then committed with an atomic conditional-write claim (first writer wins, the loser re-dispatches) plus an accept-timeout.
